## P18 icr_percent discipline  -  CONFIRMED (guard works, bounds exact); unguarded failure mode = hard rejection, never a wrong value
Code (icr.ag, exact floor of c*p*100/(SCALE*d) by hi/lo split of c on the price scale):
```
require(c >= 0); require(c <= C_MAX); require(p > 0); require(p <= P_MAX); require(d > 0); require(d <= D_MAX);
int hi = c / PRICE_SCALE; int lo = c % PRICE_SCALE;
int num = hi * p * 100 + lo * p * 100 / PRICE_SCALE;   // == floor(c*p*100/SCALE) exactly
return num / d;
```
EXECUTED-LOCALLY: 10,716 runs (1,500 random in-bounds log-uniform, 800 realistic [c 1..1e7 KAS, p 0.02..1.0, debt wide], 500 fully random int64, 2,048 extreme combinations of {0,1,2,2^31,2^32,1e8+-1,C_MAX+-1,P_MAX+-1,D_MAX+-1,int64 max}, 300 negatives, boundary pairs, 200 cases within 1 unit of ICR 150). Reference: Python big-int floor(c*p*100/(1e8*d)); int64 mirror with truncating division.
- Prediction vs engine: 0 mismatches for both versions.
- Unguarded (the audited expression): rejects exactly when c*p > 92,233,720,368,547,758 (c*p*100 > 2^63-1), on d = 0, or when the quotient does not fit; error text "Number too big: Product exceeds 64-bit signed integer range" or "Quotient exceeds ... or division by zero". No wrong value was ever returned: when it accepts, it equals the big-int reference (positive inputs). Realistic set: 601 of 800 rejected. Engine-confirmed boundaries (accept at c_max, reject at c_max+1): p=2.95e6 -> 312.66 KAS; p=1e7 -> 92.2 KAS; p=1e8 -> 9.22 KAS; p=5e8 -> 1.84 KAS. Consequence (DERIVED from vault.ag, not changed): an immutable vault with this expression cannot hold or liquidate more than those amounts.
- Guarded: accepts iff inputs inside [0,C_MAX=1e16 sompi] x (0,P_MAX=5e8] x (0,D_MAX=4e18]; 3,040 in-bounds accepted with value == reference, 2,318 out-of-bounds rejected (negatives and zeros included). Exact internal limits: hi*p*100 <= 2^63-1 and lo*p*100 <= 2^63-1 (lo < 1e8) => p <= 922,337,203 absolutely; with p <= 5e8, c up to 1.8e16 sompi (180 M KAS) is overflow-free. The guard constants are conservative choices; the hard ceilings are the two inequalities.
- Residual: P_MAX bounds the PRICE, so the oracle must enforce 0 < price <= P_MAX itself (P20), otherwise every vault entry rejects (liveness, not safety).

## P7 L1 form  -  PARTLY CONFIRMED (controller + sharded counters feasible; write-authentication of the counters UNSOLVED here)
Free/paid flag in vault state: EXECUTED-LOCALLY as `free` (0/1) in vault_redeem.ag (redeem on free=1 accepted, free=0 rejected). The `set_mode` entry is COMPILED only.
Where the aggregate lives:
1. One global counter UTXO: DERIVED from econ-t4 (6.0 to 9.6 chained spends/s on one outpoint, 80 ms submit round trip, loser refused immediately with "already spent in the mempool", no fee paid). With service time S about 0.1 to 0.17 s and utilisation <= 0.5, one counter carries about 3 to 5 flag/debt events per second; A3's S = 1 to 10 s was 6 to 100 times too pessimistic.
2. K shard counters {free, paid} (siblings of one covenant id; a vault touches only its own shard, fixed at open) plus a permissionless `poke` that co-spends all K shards unchanged, sums them, derives the direction and updates the rate. EXECUTED-LOCALLY with K = 4 (ctl.ag + shard.ag): poke accepted; r computed in-script equals Python (51,168,694 ppb for direction +1, dt = 1 day, from 50,000,000); an expected r off by 1 ppb REJECTED; dt < DT_MIN rejected; lock_time below the stored clock rejected by CLTV ("locktime requirement not satisfied"); changed shard output rejected; only 3 shards, or one shard of a foreign covenant id, rejected ("observe expects 4 inputs for its covenant id, found 3"); sum > SUM_MAX rejected. Mass of the K=4 poke: compute 5,345, transient 13,180, storage 35,660 (controller 1 KAS, shards 20 KAS). K = 32 (DERIVED from the measured oracle `use` ladder, 759 compute / 1,556 transient per input): about 26.6 k compute and 56.8 k transient, far below the limits; K up to about 600 by transient.
3. Poke success under contention (DERIVED, Poisson): P(no shard touched during window w) = exp(-lambda_total * w), independent of K. Window 0.1 / 0.2 / 0.8 s: lambda 0.1/s -> 99 / 98 / 92 %; 1/s -> 90 / 82 / 45 %; 5/s -> 61 / 37 / 2 %. Retries are free (the loser pays nothing). K divides the per-shard hot rate: K shards carry about K x (3 to 5) events/s.
4. UNSOLVED: who may write a shard. `co_spent` is presence-only (P11 case F shows the consequence), so a shard must OBSERVE the vault transition and check delta = change in the vault's debt/flag, and must identify the vault family. Vault families are per-genesis covenant ids (about 100 vaults per genesis by storage mass; 180 vaults used two ids in AUDIT 13.3b), so a closed `by covid` observation covers one family only; many families need template-based authentication (open ICC handle), which carries the hidden-mutability channel of P11. Not compiled here.
5. Vaults that need the rate must co-spend a rate-carrying sibling (an oracle-like population). A stale sibling gives a stale rate; the controller bounds the error itself: relative error <= 2^(T/H)-1 for staleness T (H = 30 d): 1 h 0.1 %, 1 day 2.3 %, 7 days 17.6 %.
Exponential controller in integer arithmetic (rate.ag; r in ppb/yr, Q30 fixed point): r' = clamp(r * 2^(+-min(dt,DT_MAX)/H), RMIN, RMAX); e^x by a degree-6 Horner series for x <= ln2/2; the decrease is floor(r*2^30/e).
- Overflow bounds (engine-confirmed at the exact ceiling): e_max = 1,518,500,116 (Q30); r*e <= 2^63-1 => r <= 6,074,001,535 ppb (607 %/yr); every other product <= 2^61 when dt is clamped to DT_MAX (x <= 372,130,559). Unguarded `raw` entry: 364 of 2,662 cases overflow (all with r > 6.07e9). Guarded entry (r in [0,RMAX], dt >= DT_MIN, dir in {-1,0,1}): 0 mismatches against the Python int64 mirror in 5,324 runs (1,500 random in range, 800 random wide, 360 extreme combinations, the ceiling pair r_c and r_c+1).
- Accuracy vs exact real 2^(dir*dt/H) (Decimal, 60 digits): max relative error 1.7e-7 (dt = 3,600 s), 1.1e-7 at DT_MAX; max absolute 88.6 ppb at r = 7e8.
- Rounding drift (sim_drift.py): each update loses up to 1 ppb (floor), both directions. 86,400 updates of 1 s over one day from 5 %/yr: 48,790,400 vs exact 48,857,998 (-0.14 %); one update per second for 30 days: 24,106,717 vs exact 25,000,000 (-3.6 %). With a minimum interval DT_MIN = 3,600 s (the entry rejects shorter dt and the anchor does not move): 24 updates per day -> 48,857,990 vs 48,857,998. So touch-spam is a bias of <= 1 ppb per accepted update, bounded to 24 ppb/day by DT_MIN; the unapplied time is not lost (the anchor stays).
- Explicit maximum rate: the RMAX clamp is in code (test 1e9 ppb = 100 %/yr); hard ceiling of this scheme 6.07e9. After a long idle one update moves at most DT_MAX worth of exponent (conservative by design).
- Fee accrual debt*r*dt/(YEAR*1e9) (acc.ag): the naive form overflows when debt*r > 2^63 or debt*r*dt > 2^63: 700 of 700 realistic cases rejected (debt 1e8..1e14 units, r 0.5 to 100 %, dt 1 h to 115 d). Split form (annual fee = (debt/1e9)*r + (debt%1e9)*r/1e9, then pro-rate with the same split on YEAR): bounds debt <= 1e18, r <= 1e9, dt <= 2 years; 2,200 runs, 0 prediction mismatches, error vs exact floor 0 to 2 units (never over-charges).
- Attack note (DERIVED, not quantified): a large free-debt open/close can move the ratio between two pokes, and the poker picks the instant.

## P9 targeted single-borrower redemption  -  PARTLY CONFIRMED (vault-side mechanics EXECUTED-LOCALLY; target choice by price incentive only; ENRK burn NOT modelled)

Batch: marginal about 5.9 k transient per extra covenant input with 3 outputs (t4 surplus K=1..3: 8,652 / 14,560 / 20,468), so about 160 per tx by transient, but storage binds (t4: 3 vaults of 12 KAS per tx).
Choosing the target without global knowledge:
 (a) price incentive (executed): a fee increasing in ICR makes the lowest-ICR vault the cheapest among those the redeemer can see; no on-chain ordering; the redeemer finds vaults off-chain (no node RPC lists UTXOs by covenant id, AUDIT 13.3). It is an incentive, not a guarantee.
 (b) best-of-K batch: the tx spends K vaults and the script requires ascending ICR among them (DERIVED, no code); guarantees only relative order.
 (c) global sorted list: needs a hot linked-list UTXO (contention of P7 item 1); rejected for throughput (DERIVED).
 (d) threshold: only vaults with ICR below a covenant constant are redeemable (DERIVED, no code).
Attack surface: (1) owner front-runs by switching to paid: both txs spend the same outpoint, one is refused ("already spent in the mempool", t4); the winner is whoever the node saw first; the loser pays nothing, so both sides retry cheaply (DERIVED). (2) Sibling choice: the redeemer picks which oracle sibling to co-spend; a stale-LOW sibling pays more collateral per ENRK: executed, p = 0.9 vs 1.0 accepted with 11 % more collateral per unit; bounded by the sibling spread = the P20 move bound. (3) Underwater vault ICR 80 %: redeem ACCEPTED at the base fee (guard absent), moving the loss to other holders; a rule ICR >= 100 % is needed (not added, design decision). (4) Dust payouts: storage mass 4e12/value, so MIN_REDEEM must keep the payout above about 8e6 sompi to stay includable (see P12). (5) Burn of the redeemed ENRK UNTESTED: KCC-20 has no burn (AUDIT 13.3); see P19.

## P10 stale-oracle degradation without a clock primitive  -  CONFIRMED as "lower bound only": decay/wind-down in favour of the party that proves staleness is possible; reduce-only for owners is impossible
Facts: a script can only prove "now >= x" (CLTV on lock_time; OpTxInputDaaScore of a spent input); finality bounds the claimed lock_time by the real accepting time; no upper bound on now exists; the round counter of a sibling is only a lower bound on the current round.
EXECUTED-LOCALLY (vault_stale.ag + oracle_b.ag; the oracle state carries `last` = DAA stamped at sweep; claimed staleness = lock_time - last, CLTV-guarded; linear decay of the price to 0 over DECAY = 864,000 DAA):
- liquidate, claimed age 0, healthy vault ICR 300 %: rejected; age DECAY/2 (ICR exactly 150): rejected; age 0.6 DECAY: ACCEPTED (compute 2,740, transient 9,080); age DECAY and 10 x DECAY (clamped): accepted. So a healthy 300 % vault is seizable once the claimed staleness is large, which is Monolith's wind-down behaviour. lock_time below the oracle clock: rejected by CLTV; oracle price 0: rejected.
- Owner side: `withdraw` to 200 % with claimed age 0 is ACCEPTED while the real staleness is arbitrary (the owner sets lock_time = last); with honest age DECAY it is rejected. So "reduce-only when stale" cannot bind owners; likewise a liquidator can understate staleness, so "liquidation disabled when stale" is also unenforceable.
Safe set: (i) decay or wind-down paid to the party that must prove staleness (liquidator, redeemer, anyone triggering an emergency settlement at the last price after last + T) is provable with CLTV; (ii) risk-increasing owner actions cannot be freshness-gated, so exposure must be bounded otherwise (P20 move bound x sibling spread, haircut); (iii) the stamp is oracle-carried: if the publisher stalls nothing moves. Unproven: DECAY and T values (design); interaction with stale siblings (a stale sibling carries an OLD `last`, so it looks MORE stale, which favours a liquidator who picks it; untested).

## P20 sweep price bounds  -  CONFIRMED (per-sweep bound executed; per-time bound needs the clock; rotation covers key loss, not compromise)
oracle_b.ag `sweep`: price in [P_MIN=1000, P_MAX=5e8] for parent and children, equal siblings, |move| <= 10.00 % of the parent, `tx.daa >= last + GAP` (GAP 600), new `last` = OpTxLockTime(); `rotate` needs old AND new signature. EXECUTED-LOCALLY: +10.00 % and -10.00 % accepted (compute 2,638, transient 3,592); +10.01 % and -10.01 % rejected; price 0 rejected; 900 < P_MIN rejected; non-publisher key rejected; lock_time one DAA before last+GAP rejected by CLTV; unequal siblings rejected; parent above P_MAX rejected; child above P_MAX rejected; rotate with both signatures accepted (compute 3,280); rotate with the new key unsigned, or the old key unsigned, rejected; after rotation the OLD key's sweep is rejected and the NEW key's accepted.
Limits: (1) the bound is per sweep of one lineage; 10 % per GAP = 600 DAA (about a minute) still allows about 1.77x per hour, so GAP and MOVE must be sized together (owner decision); without the clock field, chained sweeps in one block compound. (2) The publisher can understate `last` (never overstate), so catch-up sweeps are allowed but total movement <= real elapsed / GAP. (3) A compromised key can rotate to itself; there is no recovery key or delay without a clock. (4) Siblings not swept stay valid at the old price (stale sibling); the bound does not remove that, and P7/P9 show redeemers and liquidators can exploit the spread. (5) Vault scripts must also require 0 < price <= P_MAX (done in vault_stale and vault_redeem); the oracle bound alone does not protect an old vault script.
