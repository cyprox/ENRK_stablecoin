## 2. Language semantics and compiler guarantees (Silverscript)

- Contract = P2SH redeem script. Entries are selected by a dispatch tag; state fields are stored in the redeem script; ints are ScriptNum (max 8 bytes signed-magnitude, so -2^63 is not usable). Entry parameters are pushed in the spender's signature script. SECONDARY (docs/DECL.md, TUTORIAL, spec).
- Lowering to opcodes is direct: `*` -> `OpMul`, `/` -> `OpDiv`, no range guard (compile/expression.rs:453-457; this is HEAD, same in v1.0.0 per the repo's doc, spot-checked). VERIFIED. The pipeline (compile.rs:40-100) is: inference, static check, covenant-declaration lowering, ternary lowering, read-input-state lowering, inline functions, struct lowering, for-loop unrolling, then stack-machine codegen.
- Guaranteed checks at entry (VERIFIED compile/statement.rs:97-160, present in v1.0.0): each fixed-size entry parameter is length-checked with `OpSize ... OpNumEqualVerify` (`sig` = 65 bytes, `pubkey` = 32, `datasig` = 64; ast/mod.rs:204-206); `byte` = 1; int params must be <9 bytes; bool <2; dynamic arrays must be a multiple of the element size; struct-array leaf cardinalities must agree. Not guaranteed: array index bounds, split/slice bounds, tx input/output index bounds, arithmetic overflow, zero divisor, template lengths (all UB per spec, enforced only by the engine).
- Compile-time checks: for-loop iteration budget, resource limits, declaration validation, size limits (PRs #245, #246, #230 merged before v1.0.0). SECONDARY (PR titles).
- No dead-code deletion today, but permitted: the optimisation `lower_local_aliases` (which removes unused locals including their initialisers, cf. issue #169) is DISABLED: compile.rs:77-78 "TODO: Re-enable this once we make sure we don't optimize away fallible statements", locals.rs:1. Same in v1.0.0 and HEAD. VERIFIED. Consequence: unused-local statements with fallible calls still execute in current bytecode, but the UB spec allows a future compiler to drop them.
- Constructor parameters never read are omitted from the bytecode, so the P2SH address does not commit to them (issue #258, closed by maintainer comment "no guarantee unused constructor arguments won't be optimized away; make them part of the state"). VERIFIED (issue). Relevant to any "version tag / parameters hash" constructor commitments.
- Constant folding (#211) and other codegen-size items (#77, #80, #81, #82) are open; they are size optimisations, measured at up to ~3 KB per composed system (#218). Not correctness. SECONDARY.

## 3. Undefined-behaviour spec (Silverscript UNDEFINED-BEHAVIOUR.md, 360 lines, identical at v1.0.0 and HEAD)

Global rules (VERIFIED lines 1-25): not required to be rejected by the compiler; the compiler may remove, replace, fold or avoid evaluating any statement or subexpression that would encounter UB; if the contract completes, result is true and the spend succeeds; it may also fail; intermediate values unspecified; a failure caused only by UB is not an observable side effect the compiler must preserve; never use UB as an implicit check. Explicit `require`, time constraints, explicit termination and failed ZK proof are validation failures, not UB.

Categories (5 top-level headings, 18 UB rule groups):
1. Integer expressions: result must fit 8 signed-magnitude bytes (-2^63 not usable). UB: negation, +, -, * with unrepresentable result; division with zero divisor or unrepresentable result; `%` with zero divisor; numeric/comparison/boolean ops on a value whose run-time bytes are not a valid integer (after an asserting cast); int -> `byte[N]` when it does not fit N signed bytes (same for `int[]` elements and int state fields); bytes->int input over 8 bytes; requested width outside 0..8.
2. Arrays, strings, fixed-byte values: (a) `.length` of a statically-sized value may be replaced by the size WITHOUT evaluating the receiver (so `int[1]{1/0}.length == 1` may skip the division); same through constants, casts, function results, ternaries; (b) index must be >=0 and < length for every array type; (c) struct arrays: every leaf must have the same cardinality and byte length a multiple of the element size, `.length` is taken from one leaf only and does not validate the others, and unneeded leaves may be omitted entirely; (d) `split(i)` needs 0<=i<=len; (e) `slice(s,e)` needs 0<=s<=e<=len, counted in elements not bytes, applies to strings, pubkey/sig, struct arrays; (f) bitwise `& | ^` on byte arrays need equal run-time lengths; (g) concatenation/array literal/`append` must not exceed 1,000,000 bytes (also struct-array leaves and struct temporaries); (h) casts between byte-backed types assert layout without validating it, any later index/split/slice/bitwise/sig/state op is UB if the assertion was false.
3. Transaction and state expressions: every tx input/output selector index must be in [0, count) (value, SPK, sigscript, outpoint, sequence, DAA score, coinbase, covenant-id); low-level tx-substring needs 0<=start<=end<=len and result within max element size; k-th authorizing output / covenant input / covenant output needs k in range, and the input index of an authorizing-output lookup must be valid; state-reading expressions require a valid input index and an input whose sigscript contains the expected contract and state layout; template prefix/suffix lengths must be non-negative, within the script, non-overflowing; `readInputStateWithTemplate` supplied lengths must match the input's template layout; output-state validation needs valid output index, valid template-input index and ranges, encodable state, reconstructed script within max element size; chain-block sequence-commit lookup is UB for unknown/pruned/non-selected-chain/too-deep blocks.
4. Cryptographic expressions: malformed signature or pubkey encoding, unsupported sighash type, or malformed pubkey is UB (a well-formed but wrong signature is `false`); message-signature digest of required length; Blake2b key <=64 bytes, Blake3 key exactly 32 bytes; a cast to a fixed-size key does not make a wrongly-sized value valid.
5. Loops: run-time `for` range uses subtraction (end-start) and addition per iteration, all must be representable; the body inherits all other rules.

What the compiler may fold/assume, by the text: unused definitions (incl. the division in `int unused = 1/0`), array-literal element expressions when only `.length` is observed, struct-array leaf expressions when only another leaf is observed, and any statement whose only effect is a UB-only failure.

What the engine does (not the compiler): rusty-kaspa master `crypto/txscript/src/opcodes/mod.rs` lines 637-665 use `checked_add/sub/mul/div/rem` and return `NumberTooBig` / `InvalidState` (div by zero or overflow); `crypto/txscript/src/lib.rs:875-893` returns `Err(InvalidPubkey/InvalidSignature)` for malformed pubkey or signature, and `opcodes/mod.rs:809,832` returns `InvalidSigHashType` for a bad hash type. So today a UB integer or malformed-signature case FAILS the script rather than succeeding. VERIFIED (master, fetched 2026-11-10; the pinned a41a333 is older but the repo doc reports the same checked arithmetic there; rusty-kaspa v2.1.0 released 2026-09-22). This is consensus behaviour, not promised by the Silverscript spec.

## 5. Argent security model

Source: argent/docs/security-invariants/{README,leader-delegate-input-groups,template-frame-identity}.md (identical at HEAD; the e76ee07 clone has them; HEAD diff in docs/security-invariants is empty). The README states: "It is not a substitute for an audit of an application or its generated contracts."
- Artifact trust boundary: verification checks internal consistency only; it does not recompile the source or attest provenance; an attacker can replace bytecode and metadata together; consumers must obtain artifacts from a trusted build or compare to a separately trusted identity. VERIFIED.
- Closed app domain: a covenant ID defines the set of scripts that can appear (inputs descend from outputs the app authorised). Actor identity inside an app = (template hash, physical state length). Template hash = blake3(i64le(len P)||P||i64le(len Q)||Q). Actor frames must partition valid scripts; rejection rule: equal total length AND comparable prefixes AND comparable suffixes (conservative, false positives accepted); checked in the compiler and again in artifact verification. Not required to be unique across unrelated apps. VERIFIED. This was added in PR #55 (before e76ee07); proofs are informal (hand proofs in markdown), no mechanised proof.
- Leader/delegate: model with `c`, `I(c)`, `O(c)`, `A(i)` (outputs authorised by input i; KIP-20 says each continuation output has exactly one authorising input). Rules: R1 every cross-actor input position authenticates its actor contract; R2 delegate authenticates leader at `I(c)[0]`, rejects execution at index 0, requires `A(d)=empty`, no `become`/`spawns`; R3 every coordinated leader entry runs at `I(c)[0]`, its `consumes` cardinalities cover every non-leader input exactly once in order, authenticates each consumed actor, and every ordinary entry of a leader actor requires `|I(c)|=1` unless it has `consumes`; R4 every ordinary entry enforces the resolved cardinality of `A(i)` and validates each successor; R5 continuation closure `OpCovOutputCount(c) == OpAuthOutputCount(l)` for coordinated leaders (added in PR #63 = e76ee07); R6 a zero-continuation (`emits none`, zero-min ranges, spawn-only) consumes-free entry on a delegate-capable actor must satisfy `OpCovInputIdx(c,0) == this.activeInputIndex`. Properties 1-7: leader integrity; input closure; continuation ownership (`A(l)=O(c)`); delegate-position integrity; spawn compatibility (genesis outputs are outside `O(c)`); minimal batching restriction; actor-level scope.
- Property 7 (VERIFIED, leader-delegate-input-groups.md): delegation authenticates actor contracts, not entrypoint dispatch tags. Compatible leader or delegate entries of the same actor remain intentionally indistinguishable; several delegate entries of one actor that trust the same leader are interchangeable, and two coordinated leader entries accepting the same input shape are indistinguishable. Implication for us: any security distinction between two entries (e.g. `liquidate` vs `withdraw`, or "burn" vs "transfer") that is not encoded in state or in transaction checks cannot be enforced by delegation; use separate actors. Also, an actor's every entry can execute whenever the actor is authenticated ("account for every entrypoint that can execute within an authenticated actor contract").
- Single-actor direct input reads (`readInputState`) are used only when the app has exactly one actor and consumes its own type; the template witness is mandatory in multi-actor apps. VERIFIED.
- `co_spent` (icc-semantics.md:31-40, 104-118): `id.co_spent()` is only a PRESENCE check: "the covenant id appears as a valid input in this transaction"; presence is not authorisation scope; sound ICC needs both sides coupled (delegating side requires the authority, authority side binds/observes the delegated transition, e.g. by signature). Lowered to `OpCovInputCount(id) > 0`. Example risk: KCC20 `identifier_type == COVENANT_ID` owner passes `transfer` if the owning covenant is merely co-spent. VERIFIED.
- `observes` lowering (seen in generated `Vault.sil`, argent/build/enrk_a_vault/sil/Vault.sil): `OpCovInputCount(id)==1`, `OpCovOutputCount(id)==0`, input index from `OpCovInputIdx(id,0)`, then `readInputStateWithTemplate(idx, prefix_len, suffix_len, template_hash_const)`. Spender supplies the two lengths, but the builtin contract (std/builtins.sil, readInputStateWithTemplate doc) hashes prefix/suffix against the expected template hash (lengths are in the hash) and requires the claimed redeem script to match the input's actual P2SH scriptPubKey, so wrong lengths fail rather than authenticate a different script. VERIFIED (builtins.sil text); the implementation was not traced line by line.
- Open ICC: the observer stores an `actor_type<State>` handle; the observed implementation is "a covenant input in the same transaction that validates itself"; the observer only constrains what it cares about; the handle only fixes state SHAPE. Behaviour of the chosen implementation is whatever the stored handle points to. For an immutable CDP this is a pseudo-upgrade or governance channel and must be excluded or its trust stated. VERIFIED (icc-semantics.md:170-300).
- Spawns / genesis (README of security-invariants "Genesis spawns"): scripts cannot enumerate genesis outputs, so Argent passes witnessed global output indices and reconstructs the consensus covenant-ID preimage (active input outpoint, count, indices, values, scripts); claim 1 (complete group authenticated under hash collision resistance), claim 2 (strictly increasing first indices so one group cannot satisfy two clauses). Assumptions: consensus derives genesis ID as described, spawned actors use the version-0 P2SH layout, keyed covenant-ID hash is collision resistant. Undeclared extra genesis groups are allowed (they receive no authority). VERIFIED.
- Launch proofs / bootstrap: PR #66 (2026-10-02, HEAD, not in e76ee07) adds crate `argent-genesis` and `docs/genesis-proof-tooling.md` (473 lines): layered proofs consensus -> Silverscript -> Argent. It proves WHICH contracts and initial states started a covenant ID; the PR text and issue #57 state it does not prove the template is correct, favourable, or funded (the "what this does not prove" line is requested in #57; whether the doc includes it: UNVERIFIED, my grep of the doc for "does not prove" returned nothing). The KCC20 bootstrap (`Minter::init` via `spawns`) is a follow-up in followups.md:194-251, not implemented in the shipped example (VERIFIED at e76ee07 minter.ag has `initialized` but no init entry). Tooling for bootstrap in general: "still being built" (README).
- Fixed/introduced since the invariants doc: none of the post-e76ee07 PRs (#66-#73) alters the security-invariants docs (VERIFIED, empty diff), but #68 and #72 change codegen of template handling.

## 7. How generated Silverscript maps to opcodes (evidence)

- Arithmetic and comparison: direct opcode (`OpMul`, `OpDiv`, `OpNumEqualVerify`). `require(x)` -> condition then `OpVerify`; entry dispatch by tag; params checked by `OpSize`. Introspection: `tx.inputs[i].value` -> `OpTxInputAmount`-style opcode, `OpCovInputCount/Idx`, `OpCovOutputCount`, `OpAuthOutputCount/Idx` (visible in Vault.sil). Template hashing is blake3 (PR #163). `become next <- self` lowers to `tx.outputs[idx].scriptPubKey == tx.inputs[active].scriptPubKey` (Vault.sil, exact continuation). For the ENRK Vault: script 805 B, 604 opcodes, state 75 B, template 730 B (`argentc inspect`, 2026-11-10 run on existing build, VERIFIED).
- The exact bytecode of your contract is the artefact consensus will run. Because of UB and optimisation freedom (section 3), the faithful audit object is the compiled bytecode (disassembled) plus the generated .sil, not only the .ag source.

## 8. Can a deployed covenant be upgraded?

- No upgrade mechanism exists in either language (grep of both doc trees for upgrade/immutable/migrate/redeploy: nothing relevant; only "immutable" as a Rust-internal term in compiler-design.md:90). VERIFIED (negative grep). The redeem script is the P2SH preimage; its hash is the SPK; a continuation must satisfy the same code. A "new version" can only exist as (a) a new covenant with a separate bootstrap, (b) a state transition into a different actor/template that was already compiled into the original contract (routes `emits`/`become next <- OtherActor`, `actor enum`, `actor_type` handles), or (c) state-selected delegation (open ICC handle, `cov_id` of an authority) which can carry hidden mutability. So "immutable" is the default; mutability only enters through designed routes or ICC pointers. SECONDARY (derived from semantics).
- Also: `cov_id` observed in a state field (as in `examples/enrk`) is set at creation: a vault created pointing at a forged feed is possible, which `examples/enrk/probe_const_covid.ag` tries to answer (can the covenant id be a compile-time constant?). I could not run it; the grammar accepts `const cov_id` (probe file), result UNVERIFIED. Note a const cov_id cannot work for a covenant whose own genesis depends on the oracle id unless the oracle is launched first (bootstrap ordering).

## 9. Assessment for an IMMUTABLE contract

Safe-to-rely-on candidates (with the caveat that nothing is externally audited):
- Plain arithmetic whose operands are explicitly bounded by `require` before use (see 3); the engine checks arithmetic today, but that is a consensus detail not promised by the spec (a hardfork could change it).
- `checkSig` with `sig`/`pubkey` typed parameters (length-checked at entry, 65/32 bytes, malformed encodings fail in the engine today).
- Exact continuation (`become next <- self`, SPK equality), `OpAuth*` based output enumeration, `emits`-declared fixed output shapes, `require`-based value checks.
- Template-authenticated cross-actor state reads (`readInputStateWithTemplate`: hash plus SPK match) inside a single compiled app, with Argent's pairwise-disjoint frame check.
- Genesis `spawns` (claims 1-2) and the genesis proof tooling for launch verification.
- Single-actor apps with direct input reads; single leader plus fixed delegates with properties 1-6.

Not safe, or not enough evidence:
- Anything that depends on UB-as-check: unbounded `*`/`+`, division without `require(d != 0)` (your vault `icr_percent` is exactly this; 100% of vaults > ~9.2 KAS fail, which for an immutable contract equals permanent inoperability), indexing/slicing without explicit bounds, negative or oversized template lengths, struct-array lengths from user input, casts that assert layout, `for` ranges from run-time values.
- Reliance on the current bytecode preserving unused fallible statements. Argent's generated `readInputStateWithTemplate` binds its result to a local that variant A never uses (Vault.sil: `gen__oracle_round_state`); the authentication of the oracle input then rests on a statement whose result is unused. Today it is kept (alias lowering disabled, compile.rs:77-78); the UB spec lets a later compiler drop it. For an immutable contract this is a build-pinning matter (audit the bytecode that is actually deployed), not a runtime risk, but it must be on the audit list and the build must be locked. VERIFIED (source), execution not tested.
- `co_spent` as an authority check; open ICC handles; `Minter` observed-proxy patterns without a full bootstrap proof; cross-app composition at fingerprint-divergence edge cases (#31 closed, but the pattern is young).
- Entries of the same actor distinguished only by entry (Property 7); multi-actor apps with ambiguous frames (conservative rule blocks them, but then fails to compile).
- Mixed `readInputStateWithTemplate` + `validateOutputState` entries until #252 is resolved (liveness hazard).
- Any dependency on compile-time cost or budget: no worst-case estimate (#243); a CDP entry must be tested at maximum realistic input counts under the engine's script-unit limits.
- Unused constructor arguments; "version" fields in constructors.

## 10. What an audit of "our source + Argent lowering + Silverscript" would require

Scope (all three layers, same bytes):
1. ENRK source (.ag): arithmetic discipline per entry (bounds on every operand, divisor non-zero proofs, accepted input ranges), logic (oracle freshness, genesis price constraint, liquidation/auction economics), state encodings, value conservation (`unrestricted(...)` must be justified), Property-7 review for every actor with several entries, delegate/leader configuration, absence of open ICC and `co_spent`-only authority.
2. Argent lowering: generated .sil for every actor (the repo says "plain, auditable Silverscript"), route plans, template/frame disjointness, observed covenant checks, spawn lowering, witnesses (template lengths as spender-controlled arguments), artifact id and interface fingerprints; review of compiler passes where route fields and caller-supplied state interact (PR #45 class bugs) and of the 6 leader/delegate rules against the generated opcodes (R5/R6 check expressions present). Argent is itself self-described as needing audit; the invariant proofs are informal markdown.
3. Silverscript: semantic rules vs bytecode for the constructs actually used (not the whole language): stack-binding/codegen, struct flattening, state encoding/decoding, `readInputStateWithTemplate`, `validateOutputState*`, ternary/loop lowering, entry param validation, dispatch tags. Use a narrow subset policy: ban features that were buggy historically (struct arrays, tuple split on State[], ternary with fallible branches, shadowing, loops with run-time bounds).
4. The deployed bytecode: disassemble every entry, check it against the .sil, and run the final artifact on the pinned engine (rusty-kaspa 2.1.0). Treat the bytecode (redeem script hash, template hash, artifact id) as the audited object; lock compiler and Argent revisions; require reproducible rebuild from a clean checkout.
5. Consensus assumptions: KIP-20 covenant semantics (single authorising input per continuation, `OpCov*`/`OpAuth*` semantics, covenant-ID derivation), script-unit/compute-budget limits and mass (KIP-9) under worst-case transactions, ScriptNum behaviour, rusty-kaspa version pinned.

## 11. Review of docs/design/UNDEFINED-BEHAVIOUR-EXPOSURE.md and examples/enrk

Checked against the spec (VERIFIED where cited):
- Claims confirmed: spec contents, bare `OpMul`/`OpDiv` (expression.rs:453-457), engine checked arithmetic (opcodes/mod.rs:651,658), the 922 KAS / 9.2 KAS ceilings (8-byte limit 9,223,372,036,854,775,807; correct arithmetic), `icr_percent` unguarded (a/vault.ag and b/vault.ag), generated args `gen__oracle_feed__price_round_{prefix,suffix}_len` (build output), `sweep` bounds in variant B.
- Internal inconsistency: section 1 says "Four of the eight categories are absent" but lists five items; the spec has 5 headings (the "eight" is an own grouping). Minor.
- The open question in section 3 (malformed `sig`) can now be partly closed: (1) `sig` entry parameters are length-checked to exactly 65 bytes by the generated entry prologue (compile/statement.rs:97-160) in v1.0.0; (2) the engine returns an error, not true, for a malformed pubkey, signature, or hash type (rusty-kaspa lib.rs:875-893, opcodes 809/832). What remains UB-only is the case where a future compiler/engine changes either. Severity "maximal" is therefore not realised today; it should be restated as "formally UB, currently fails". Also the oracle's `publisher` pubkey is a constructor/state value, so the malformed-key route is not spender-controlled in the oracle.
- The open question in section 4 (spender-supplied template lengths) can be closed to a large extent: the template hash commits to both lengths and the claimed redeem script must equal the input's P2SH script (builtins.sil doc, step 4-5); wrong lengths fail rather than allow another template. Residual: UB formalism and #252.
- Missing from the analysis:
  1. Unused-local authentication (section 9): in variant A the observed-oracle `readInputStateWithTemplate` result is unused in generated Vault.sil; the UB spec permits removal; currently preserved because `lower_local_aliases` is disabled. Not mentioned in the exposure doc.
  2. The spec rule that `.length` of fixed-size values need not evaluate the receiver, struct-array leaf omission, and "Intermediate expression values are not specified" - not applicable to the five files but relevant once `Item[]`/state vectors appear in the real design.
  3. `tx.inputs[this.activeInputIndex].value` and `OpCovInputIdx(c,0)` indexing are in-range by construction, but `OpAuthOutputIdx(active, 0)` and `tx.outputs[idx]` rely on a preceding `OpAuthOutputCount(...) == 1` require in the generated code; the doc says transaction-index rules apply to generated code but does not confirm they are discharged (they are, in Vault.sil: `require(OpAuthOutputCount(this.activeInputIndex) == 1)` precedes idx use). 
  4. `withdraw` arithmetic: `next.value == self.value - withdrawn` is bounded only by `withdrawn > 0`; no overflow possible (self.value < 2^63), a point the doc could state to avoid over-claiming.
  5. Fixed-width integer state encoding: the compiler comment (compile.rs:246) says int-like values occupy the full eight-byte payload, which answers the doc's "width not verified" point for `round`, `price`, `debt` (int state fields of 8 bytes; writing an int that fits ScriptNum is always representable). Still verify per-field.
  6. Constructor arguments dropped when unused (#258) and COMPILER_VERSION pragma mismatch: affect "what the P2SH address commits to".
  7. Argent HEAD vs e76ee07: PR #67 (co-spend precedence), #68/#73 (template hash and name changes) mean re-measurement on the newer revision would change template hashes and sizes; the doc pins e76ee07/v1.0.0, which is fine but should say "HEAD differs".
  8. Variant A `use` lacks condition (a) (acknowledged), variant B genesis price unconstrained (acknowledged), `liquidate` with `emits none` has no continuation closure; a/vault `liquidate` is also not constrained by `OpCovOutputCount` of the vault covenant itself (`emits none` -> `OpAuthOutputCount == 0` only). These are stub-level, not UB.
  9. Oracle freshness, price bounds (`price > 0` in A: UTXO value can be 0? value is an output amount, dust rules: UNVERIFIED), and `sweep` in A has no check on value conservation ("unrestricted"): an attacker with the publisher key can drain; by design for a stub.
  10. `probe_const_covid.ag` compile outcome is not recorded in the exposure doc (the file header says either outcome is the answer). UNVERIFIED here.
- `examples/enrk/{a,b}` themselves contain only measurement stubs (VERIFIED); no loops, casts, arrays, slices; the only UB-relevant operations are the arithmetic in `icr_percent`, `round + 1`, `self.value - withdrawn`, `self.value - left_value`.
