## 2. econ-w1 (unit variants and re-base)

X-2 (CONFIRMED, low) Spend reconciliation: ledger has 72 SUBMITTED rows (matches "72 accepted"), 9 REJECTED, 2 ERROR (matches §8: 5 split orphans, 3 stale attacks, 1 drain; 2 DNS errors). X-3 (CONFIRMED, medium) Over-claimed provenance for N >= 47 on form (b): the refusal figures "N = 47: compute 507,273 > 500,000; N = 48 522,964; N = 64 853,920; N = 96 1,751,132; N = 128 redeem script 274,369 bytes" do not appear in any saved log, ledger or script in sources/econ/x1b (I grepped the whole folder; only the (a) N = 16 message 1,057,220 is in logs/local_a_n16.txt). The quadratic fit c(N) = 3,602 N + 151.6 N^2 (3 parameters-worth of data, 2 parameters) predicts 504,178 at N = 47, i.e. 0.6% below the reported refusal, and is 3% off at N = 4 (16,834 vs 17,346); "within 0.2%" holds only at the three fitted points 16, 32, 46. Proposal: save the builder refusal outputs for N = 47..128 next to the logs.

X-4 (PLAUSIBLE, medium) "Population N is bounded by about 46" is a property of this contract form, not of Kaspa L1: the quadratic compute term comes from `ns = ns.append(nx)` inside the loop (report: "array append in the loop"), and (b) is bound by compute 500k while transient would allow about 83. The project memory and PROJECT-STATE headline "whole-population refresh works but max N = 46" drops the qualifier. A different layout (several smaller populations, a tree of rounds, or a non-appending loop) would move the bound; none was tested. The report body says "bounded by about 46 with this form"; the downstream summaries are looser.

X-5 (CONFIRMED, low) Negative control: the on-chain result is real and well recorded: partial refresh tx 9521f602... (ledger refresh_partial_ctl4_1), stale withdraw 56f30dfc... mass 11,990 accepted (confirm 9.8 s), the control contract differs from the guarded `refresh` only by dropping the `n`/slot requirement (diff of a/n4 vs actl/n4: `refresh_partial` has no `olds.length + 1 == n`, no `slot == i+1`, no `o.n == n`, and keeps round/price equality), and the vault.ag is identical. Limits: (i) the "fresh sibling rejected, ICR 189" comparison is local only; by the stated parameters (3.0 TKAS collateral, withdraw 1.0, debt 1.0, price 0.90) I compute ICR = 180, not 189, so there may be an unreported extra value in the vault UTXO; (ii) the guarded counterpart's refusal of the same partial refresh is local only (builder cannot emit), so the pair "attack accepted without guard / refused with guard" is chain-demonstrated on one side and engine-demonstrated on the other; (iii) the control removes `n` and `slot` checks together, so it does not attribute the protection to one of them; (iv) variant (a), N = 4 only.

X-6 (CONFIRMED, low) Wording: "a vault reads a price that is two rounds old, forever". In csc.py the STALE withdraw is submitted immediately after the FIRST partial refresh, so the stale sibling is one round behind (round 1 vs round 2, price 1.00 vs 0.90). Later partial refreshes (rounds 3, 4) happen after the withdraw. "Forever" (never refreshable by the guarded entry) is correct; "two rounds" is not what was executed.

X-7 (PLAUSIBLE, low) Stale-sibling attacks 1-3 are refused by the node with the generic "orphan" message. The report's reasoning (outpoint already consumed by the refresh) is sound and flagged DERIVED; but these three tests only show that a consumed outpoint cannot be spent again, a base-layer property that does not exercise the covenant guard. The covenant-level protection against partial refresh rests on X-5. Also untested: a vault transaction already in the mempool when the refresh lands (race: the refresh consumes all N siblings, so any pending `use` or vault read of a sibling is invalidated); a liveness question for a design that reads the oracle by spending it.

X-8 (CONFIRMED, info) Contracts read: the guards listed in §1 exist in b/oracle_4.ag (`olds.length + 1 == n`, per-sibling `slot == i + 1`, same round, same price, same `n`, `news.length == olds.length`, value preserved, +/-10% bound, publisher signature). `delegate follow` requires `lead.round == round`. No guard binds a vault to `n` or to a specific population: the population identity and `n` are whatever the publisher-signed genesis wrote (trust assumption; the report says the key is trusted: "tests structure, not key compromise"). `drain` lets the publisher destroy followers alone, which would freeze the population (liveness only).

X-9 (PLAUSIBLE, low) Unverifiable by me: that no covenant value remains locked (API listing of 73 plain UTXOs); the claims about node refusal "same limits node-enforced" at N = 47 (local builder only); mass for transient/storage is the local MassCalculator (the API reports compute only; the report says so in §9).

W2-2 (REFUTED, info) Concern: the shared pre-year snapshot in w2_run.py (key = fee, speculator set, size) could be wrong for other architectures/profiles, and check_w2 part (3) tests only a per-scenario snapshot. W2-3 (REFUTED, info) Concern: RNG pairing / draw counts. Code read: speculator/miner class and attention use `_prng` seeded by `seed * 1_000_033 + 91`, two draws per vault, sets nested by thresholds; the owner pass draws one number per vault per day including dead vaults; the crash RNG is never touched (build_population consumes it before the rb block). W2-4 (CONFIRMED, medium) Wrong description of V1's labels. Summary point 5 and §7 say "V1's own labels (ENRK p95 <= 5, unbacked <= 3, latent p95 <= 1; not mine)". V1's header (analyze_v1.py line 5) defines SURVIVE = ENRK p95 <= 2 AND latent p95 <= 1 AND unbacked <= 3, and HOLD = ENRK p95 <= 5 AND latent p95 <= 1. The W2 text mixes both. Recomputed from HL.pkl over the 7 bases: under the hybrid (5/1/3) CENTRAL_R gives A3 1/7, A5 5/7, STACK 5/7 (as the report says); under V1's SURVIVE: A3 0/7, A5 1/7, STACK 5/7; under HOLD: A5 5/7, A8 7/7, STACK 7/7. The statement "with the holder run A5 and STACK pass all three in 5/7" is therefore true only for a label that does not exist in V1. The passive/central/hostile statements (A3 and A5 0/7, STACK ENRK-only 7/7 passive and central, unbacked 0-1/7) are correct under any of the variants.

W2-5 (CONFIRMED, low) Latent label knife-edge. The latent p95 is 0.0 when the hole share is below 5% and 3.9-4.8 when above (A3 flat85: S0 4.2% -> 0.0; CENTRAL_B 5.0% -> 3.9; HOSTILE_B 5.8% -> 4.7). The report discloses this. Consequence: in N0 / CENTRAL_B / HOSTILE_B the "latent <= 1" criterion fails in 0/7 cases only because shares sit at 5-7%; the label passes with the run only because shares drop to 1.4-2.8%. So label counts in point 5 are driven by a quantile threshold, not by the hole size.

W2-6 (CONFIRMED, medium) Summary point 4: "junior net per cycle is negative for A3 in every profile except the friendly upper bound". On the full 7 x 13 grid A3 junior net is positive in: flat70 EXIT +1.7, DEF +2.3, CENTRAL_R +2.9, FRIENDLY +8.8; x1.5@70 EXIT 0.0, DEF +1.5, CENTRAL_R 0.0; ep2024 EXIT +1.1 (and FRIENDLY on all 7 bases). The sentence holds for the three -85% bases only (the example numbers are flat85). Further, the E_w conclusion in §6.2 ("a junior needing h = 10% fails in all A3/A8/STACK cells and all A5 flat85 cells") is close to tautological: calm yield is r/s = 10.0% of face, so E_w = 0.9 x 10.0 + 0.1 x net can reach 10 only if net >= 10, which only FRIENDLY_B reaches. The result is set by h versus r/s, almost independent of crash behaviour. Presenting it as "robust self-consistency problem" overstates what the behaviour sweep adds. The fee-income assumption (entire 3% fee goes to a 30% junior, no demand loss) is inherited from W1.

W2-7 (CONFIRMED, medium) Claim "91 of 91 ordering is robust". I reproduced it: for all 7 bases x 13 profiles, ENRK p95 satisfies A0 >= A3, A3 >= A5, A3 >= A8, A8 >= STACK, and unbacked A5 <= A3, STACK <= A8 (no violation). But: (a) it is a point-estimate ">=" with 7 tied zeros; (b) 26 adjacent comparisons are within 0.3 points; (c) on 364 paired bootstrap comparisons of p95 differences, 12 have a CI that includes 0 (all FRIENDLY_B); (d) much of it holds by construction: A5 = A3 plus S3 (surplus destination only), A8 = A3 with a larger junior share. In every no-run profile unbacked is exactly identical for A3 and A8 (63 of 63 cells) and for A5 and STACK, so "S3 protects the hole more than A3" and "A5 <= A3" are accounting identities of the model, not empirical robustness; (e) all architectures share one simulator family. Also "junior 50% protects ENRK more at the price of more kFIAT loss" is true in absolute debt terms (91/91) but false in the reported metric: kFIAT mean loss as a share of kFIAT face is LOWER for A8 than A3 in 91/91 cells (e.g. flat85 N0 28.2 vs 35.0). Proposal: say "ordering unchanged" (not "robust") and give the kFIAT loss in the same unit as the claim.

W2-11 (PLAUSIBLE, medium) The strongest "friendly" levers rest on frictionless exits. The slippage sweep 0 -> 10% changes ENRK p95 by only +/-0.2, showing the effect is the bypass of discount and capacity. FRIENDLY_B means 73% of opening debt value injected from external funds and 75% of debt self-liquidated with 2.28 days of ADV of KAS sold. Disclosed in §8 as "repayments at face, impact end of day", but not cited as the reason EXIT/DEF dominate. Cash exit never fires at budget 0.15 (disclosed).
